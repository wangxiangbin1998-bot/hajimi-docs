# 合伙人百分比返佣 · 外挂结算规格

站点：哈吉米 API（New API v1.0.0-rc.47，price=1，quota_per_unit=500000，即 500000 额度 = ¥1）
背景：官方 New API 至今未实现充值百分比返佣（文档写了「返利比例」但代码没有；GitHub issue #7080 已标 Not planned）。本站不改 New API 源码（2026-10-28 既定规矩），用外挂脚本读库算佣、写回邀请账本实现自动返佣。

## 一、四条口径（用户 2026-11-04 亲口拍板）

1. **计佣范围**：只有「云猫寄售卖出的兑换码」被兑换入账才算。在线支付（top_ups）、管理员手动入账、非云猫兑换码，一律不算。
2. **计佣基数**：兑换码面额（`redemptions.quota / 500000` = 元）。云猫向买家收的手续费不计入基数。
3. **不冻结**：兑换入账即具备结算资格，脚本每次运行把全部未结算记录一次结清。退款靠后续扣回（见第四节待办）。
4. **阶梯比例**：按邀请人名下「累计有效用户数」定档——
   - 0–49 人：5%
   - 50–99 人：7%
   - 100–199 人：8.5%
   - 200 人及以上：10%
   - **有效用户** = 被邀请人累计兑换云猫码面额 ≥ ¥3（按全量历史累计，含已结算过的记录）。2026-11-07 站长定：门槛由 ¥10 降到 ¥3（最低充值 ¥2，¥3 等于让用户多充一次才成有效）。
   - 比例作用于每一笔兑换，取结算时该邀请人所处档位。

> **2026-11-07 晚修订（站长拍板，覆盖上面第 4 条的有效用户定义）**：有效用户改按**全渠道累计付费**算——被邀请人的全部批次兑换码兑换面额 + 在线充值成功订单（top_ups，status=success）实付金额，合计 ≥ ¥3 即有效，不再只认云猫批次。原因：合伙人页一直写「累计充值满 ¥3」，引擎只认云猫造成两边对不齐，现按页面口径改引擎。**计佣范围/基数不变**（第 1、2 条不动，返佣仍只结云猫码）。settle.py、affcode.py（申请门槛）同口径已改；免费池的有效邀请数读引擎发布的 effective_users，自动跟随。另新增**邀请奖励补发**：被邀请人注册于 2026-11-10 00:00（+08:00）之后且累计付费满 ¥3 时，引擎给其邀请人补发 ¥1（aff_quota/aff_history），账本 affiliate_invite_bonus 防重，配合 11-10 原生 QuotaForInviter 改 0 的切换。补发另有**活动截止**口径：被邀请人注册时间须 < 2026-12-21 00:00（+08:00），即活动至 2026-12-20 截止，2026-12-21 起注册的被邀请人不再触发补发（settle.py 常量 INVITE_BONUS_START / INVITE_BONUS_END 双界；窗口可覆盖：--bonus-start/--bonus-end（epoch 秒）或环境变量 AFFILIATE_BONUS_START/AFFILIATE_BONUS_END，命令行优先于环境变量，不填用常量默认）。

> **2026-11-08 晚修订（站长批准，dsh 独立复核后修，覆盖/补充上段补发口径）**：
> - **孤儿校验**：补发付款前先校验邀请人用户行存在；`inviter_id` 指向不存在的用户行 → 跳过该笔、日志告警、**不写补发账本行**（留待后续轮次再评估，不记成已处理）。补发入账 `UPDATE aff_quota` 后校验 affected rows 必须 =1，为 0 则抛错、整事务回滚（防止账本记了已发、钱却无声蒸发）。
> - **充值取数定死**：累计付费（有效用户与补发触发共用口径）里的 top_ups 只认 `status=success` 且 `money>0` 的订单、按 `money`（元）计；`money≤0` 或为空的订单计 ¥0。原先 money 为 0 时拿 `amount` 当 quota 的回退分支已删除（amount 语义不可靠）。兑换码面额口径不变。
> - **四种不补情形**（结算时点判定）：①邀请人已封禁（status=2）；②被邀请人已封禁（status=2）；③邀请人已软删（deleted_at 非空）；④自邀（inviter_id == 被邀请人自身 id）。四种一律：跳过＋日志写明原因（`invite-bonus-skip`）＋**不写补发账本行**，后续轮次可再评估。补发后退款致累计跌破 ¥3 **不追回**（维持原口径）；管理员号不特殊处理。

## 二、识别规则（关键，运营必须守）

- 脚本识别云猫码的**唯一依据**：`redemptions.name` 以「云猫」开头（如「云猫50元卡」「云猫10元卡」），且 `status=3`（已兑换）、`redeemed_time>0`、`used_user_id>0`。
- ⚠️ **以后在本站新建任何要上云猫卖的兑换码批次，名称必须以「云猫」开头**，否则脚本认不出来、这批码不产生佣金。反之，不想计佣的码（补偿码、赠送码等）名称绝不能以「云猫」开头。
- 邀请关系取 `users.inviter_id`（注册时由邀请码绑定，事后不变）；兑换人无邀请人（inviter_id 为 0/空）的记录跳过、不结算。

## 三、表与字段依据（rc.47 实查）

| 用途 | 表.字段 | 说明 |
|---|---|---|
| 兑换记录 | `redemptions.id / .name / .quota / .status / .used_user_id / .redeemed_time` | status=3 为已兑换；quota 为面额（额度单位） |
| 邀请关系 | `users.id / .username / .inviter_id` | 被邀请人指向邀请人 |
| 佣金落点 | `users.aff_quota`（邀请额度余额）、`users.aff_history`（历史累计邀请额度） | 仿原生邀请账本：原生注册奖励就是发到 aff_quota、用户自助转入主余额；本脚本同路写入，两字段同步增加 |
| 结算账本（脚本自建） | `affiliate_settlements` | `redemption_id` 唯一键 + inviter_id / invitee_id / face_quota / rate / commission_quota / created_at；一笔兑换只结一次，重复运行不重发（幂等） |

佣金换算：`commission_quota = round(face_quota × rate)`，额度为整数；报表同时给元与额度两种口径。

## 三·五、数据桥：把返利统计发布到用户自己的 setting（2026-11-04 新增）

目的：让用户在站内 /referrals 页看到自己的档位、有效用户数、返利记录（原版 New API 没有这些字段的展示）。做法是**数据桥**——脚本把统计写进每个邀请人自己才读得到的字段，页面同域调原生接口读，不加任何新接口、不改源码。

- **载体**：`users.setting`（JSON 文本）里的自定义键 `hajimi_aff`。实验室 rc.47 已实证（2026-11-04）：
  - users 表有 setting 列；`GET /api/user/self`（登录态）返回 `setting` 原文，页面 JS 可读；
  - 合并写入自定义键后，钱包页/资料页渲染正常；用户在资料页保存通知偏好（前端整表回写 setting）**不会**带上未知键——实测保存后 `hajimi_aff` 被整表覆盖丢失（见本节末「已知行为」），靠本脚本每天凌晨重发自愈；
  - 可见性：只有本人 `/api/user/self` 和 root 的管理员用户列表（`GET /api/user/`，普通用户调用返回 AUTH_INSUFFICIENT_PRIVILEGE）能看到 setting；公开接口（pricing/rankings/status 等）不含 setting。统计只写邀请人本人的行，等于只给本人看。
- **发布内容**（`hajimi_aff` 对象）：`v`（版本）、`updated_at`、档位名/比例、有效用户数、邀请总人数、下一档 `{name, at, gap}`（满档为 null）、累计佣金（元，账本求和）、最近 20 条返利记录（结算时间/来源用户名/计佣金额/佣金/当时比例）、邀请名单（上限 100：用户名/注册时间/累计兑换云猫金额/是否有效）。
- **补发累计字段（2026-11-08 新增）**：载荷另含 `total_bonus_quota`（原始额度）与 `total_bonus_yuan`（元），为该邀请人累计收到的邀请奖励补发额——来源是补发账本 `affiliate_invite_bonus` 按 `inviter_id` 聚合 `SUM(bonus_quota)`，账本表不存在或无记录时为 0。**与累计佣金（`total_commission_quota` / `total_commission_yuan`）分列**，让邀请人在统计里能看出补发的 ¥1 来源，不与返佣混算。只加字段、不改既有键与 `v` 版本语义，旧版皮肤读不到新键无妨（向后兼容）。
- **写入纪律**：只在 `--apply` 时发布，且与结算同一事务（失败整单回滚）；影子模式只报将发布人数、不写。合并写：先解析现有 setting（JSON 对象才合并），**原有键一律保留**；现有 setting 为空按空对象处理；**解析失败或不是 JSON 对象 → 跳过该用户并告警、保留原值不覆盖**，等其 setting 恢复合法后下一轮自动补发（自愈）。
- **兜底**：脚本只写 `json.dumps` 产物，不可能写出损坏 JSON；长度上限由名单 100 人＋记录 20 条封顶（约十几 KB），远低于 text 列上限。页面侧对 setting 缺失/解析失败一律走空态（默认 5% 档），不报错。
- **已知行为（前端整表回写）**：rc.47 前端保存个人设置时提交的是它认识的键集合，未知键会被丢弃——即用户改一次偏好，`hajimi_aff` 会消失到下一次凌晨结算重发为止（最长约 1 天），期间 /referrals 显示空态。这不丢钱（账本与 aff_quota 不受影响），可接受；若日后要根治，只能改前端或换载体，另行评估。
- **统计发布不加访问闸门**：数据只存在用户自己读得到的字段里，没有页面入口时外界无从查看；闸门是展示页（Worker）的事，与发布无关。页面的闸门规则见第七节。

## 三·六、防刷标记层（2026-11-04 新增，只标记不拦截）

借鉴官方仓 PR #6539 的 commission_guard 思路，但**不改即结口径、不扣留佣金**：标记只出现在每轮报表/日志里，供站长人工复核。

- **同注册 IP**：邀请人与被邀请人注册 IP 相同 → `flag | same-ip`。前提是 users 表有注册 IP 字段（脚本按候选列名 register_ip/reg_ip/signup_ip/ip 动态探测）；**rc.47 的 users 表没有注册 IP 字段，此项自动跳过并在日志注明**（`flag-check | 同注册 IP 检查跳过`）。日后若换了带该字段的版本，自动生效。
- **单日激增**：单个邀请人单日新增被邀请人 > `DAILY_INVITEE_ALERT`（常量，现 20）→ `flag | daily-spike`；只看近 `FLAG_WINDOW_DAYS`（现 7）天，避免历史噪音。
- **人工黑名单**：`denylist.txt`（脚本同目录，可用 `--denylist` 或环境变量 `AFFILIATE_DENYLIST` 指定；每行一个 user id，# 为注释）。名单内邀请人**照常结算**，逐笔行尾加 `[黑名单标记]`，报表末尾另有一条 `flag | denylist` 汇总其本期面额与佣金。**默认不拦截发放**，是否拦截等站长后续定。
- 无任何标记时日志输出 `flag | 无异常标记`。

## 四、运行方式与上线步骤

脚本：`settle.py`（参数 `--db` 数据库路径；默认影子模式；`--apply` 才写库，账本写入与 aff_quota 更新在同一事务内，异常自动回滚）。

1. **实验室验证（已完成，2026-11-04）**：在实验室库副本 test.db 上造数实测——影子 → apply → 再 apply，数字与预期一致、第二次新增 ¥0。证据见 `evidence-2026-11-04.txt`；`test.db.golden` 为造数后未结算的干净副本，可随时重跑。
2. **生产影子期**：脚本连生产库只读跑（不带 --apply），连续跑若干天，每次报表人工核对：纳入的 redemption 是否都是真云猫码、金额与云猫后台销量是否对得上。
3. **生产适配（已完成，2026-11-04）**：脚本已改双驱动版——`--db` 传路径走 SQLite、传 `postgres://` DSN（或环境变量 `AFFILIATE_DSN`）走 psycopg，两边 SQL 兼容；已用真 PostgreSQL（pgserver 临时实例，数据由 golden 副本导入）实跑影子/apply/幂等/失败回滚，数字与 SQLite 版一致（证据见 `evidence-auto-2026-11-04.txt`）。连接串等凭据只放服务器本地 `/opt/affiliate-settle/affiliate.env`（600），不进仓库。
4. **开自动发放**：影子核对无误后按 `DEPLOY.md` 上线顺序执行 `install.sh` 开 cron（每天凌晨 03:47 `--apply`）；部署与回滚细节见同目录 `DEPLOY.md`，自动模式的运行规则见第六节。
5. **上线前检查**：存量云猫批次名称是否都以「云猫」开头；合伙人页面/公告口径与本规格一致（比例、有效用户门槛、不冻结）。

## 五、待办与已知缺口

- **退款扣回未实现**（原型阶段）：用户退款后，已发给邀请人的对应佣金目前不会自动追回。实现思路：结算账本已有逐笔记录，后续版本定期扫已结算 redemption——若对应订单发生退款（云猫侧退款/码作废），按原 rate 生成负数冲销行并从邀请人 aff_quota 扣回（aff_quota 不足时扣到 0 并记录欠额）。上线自动发放前应补上或明确人工处理流程。
- **档位跨档时点**：现口径为「结算时定档、全笔按当前档位」。被邀请人把邀请人顶进新档位的那一笔，本身也按新档位计（因为定档用全量累计、含本期记录）。若以后想改成「逐笔按当时档位」，需改算法并在此注明。
- 提现（佣金转现金）不在本脚本范围：佣金以站内额度形式发到 aff_quota，用户转入主余额消费；现金提现仍按人工私聊核对流程。

## 六、自动模式（生产运行规则，2026-11-04 用户拍板：自动发放）

- **频率**：服务器 cron 每天凌晨 03:47 跑一次 `settle.py --apply`（入账即结、不冻结；前一日 00:00–24:00 的新兑换在次日凌晨结清）。改频率只改 `/etc/cron.d/affiliate-settle`。2026-11-07 站长定：由每小时整点改按日（03:47，落在 02:00–08:00 后台窗口内）。
- **单实例锁**：脚本启动先抢文件锁（flock 非阻塞；PG 模式默认 `/tmp/affiliate-settle.lock`，SQLite 模式为 `<db>.lock`，可用 `--lock-file` / `AFFILIATE_LOCK` 覆盖）。抢不到说明上一轮还在跑，本轮直接跳过并以退出码 3 结束——不排队、不并发，防 cron 重叠双发；账本 `redemption_id` 唯一键是第二道幂等防线。
- **日志**：结构化文本日志（时间戳 + 级别），每笔结算一行 `settle redemption #…`，每轮一行 `summary` 汇总（邀请人数、笔数、计佣面额、佣金）；`--apply` 前先打一行 `[ledger-backup]` 记录账本当前行数与佣金总额作备份点，apply 后再打一行账本现状。日志文件 `/opt/affiliate-settle/settle.log`，logrotate 周轮转、留 8 份压缩档。
- **失败即停**：任何异常整事务回滚（账本与 aff_quota 要么全写、要么全不写，实测连账本建表 DDL 都能回滚），脚本以非零码退出（1 结算失败 / 2 参数或驱动问题 / 3 锁占用跳过），**不重试、不连发**，等下一个凌晨自然再跑；已结算记录靠账本唯一键跳过，不会补发重发。
- **人工介入点**：日志出现 ERROR 或退出码 1 时才需要人看；日常只需偶尔抽查 `summary` 行与账本总额（对账 SQL 见 DEPLOY.md 第五节）。停发与冲销流程见 DEPLOY.md 第四节。

## 七、/referrals 邀请返利展示页与访问闸门（2026-11-04 新增）

- **页面**：单文件 `skin-worker/referrals/index.html`（奶油猫咖风，无外部依赖），由站点 Worker 在路径正好等于 `/referrals` 时同域直出（不回源、不注入皮肤）。页面 JS 用站内登录态走与官方前端同一套机制（刷新 Cookie 换访问令牌）调 `GET /api/user/self`，读原生字段（aff_code 拼 `/sign-up?aff=` 邀请链接——rc.47 原生格式已在实验室钱包页实证、aff_count、aff_quota、aff_history_quota）＋ setting 里的 `hajimi_aff` 统计。区块：四张统计卡、升档进度条、邀请链接（带复制）、我邀请的用户表、返利记录表、规则说明。无统计时走空态（默认普通合伙人 5%），不报错。
- **访问闸门（站长 2026-11-04 定）**：Worker 顶部常量 `REFERRALS_PUBLIC = false` 为自测态——页面壳照常返回，但页面 JS 拿到用户信息后先判角色：只有站长本人（root，role=100）继续渲染真实数据；普通用户与未登录访客只渲染一个朴素的「404 · 页面不存在」假象页（不加载返利数据、不露出任何返利字样、标题也换成 404）。全站（皮肤侧边栏等）**不注入任何 /referrals 入口链接**，自测期只能直接输 URL 访问。
- **上线三段（部署细步见交付回报）**：①带闸门部署（Worker 换 v2.9.0、settle.py 更新到新版，闸门保持 false）→ ②站长用 root 账号打开 /referrals 自测（数字对账本、手机各看一遍）→ ③站长点头后把 Worker 里 `REFERRALS_PUBLIC` 改 true 重新部署，开放给全部用户。注意：统计发布（第三节·五）本身不设闸门——数据只躺在用户自己读得到的字段里，没有页面入口时不可见。
